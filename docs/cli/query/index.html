Documentation / CLI

transcript-lake query

Execute operator-supplied DuckDB SQL after loading the canonical Lake views.

Invocation#

sh
transcript-lake [--data-dir <path>] query [--json] "<sql>"

Purpose#

Execute operator-supplied DuckDB SQL after loading the canonical Lake views.

Inputs and options#

  • Required <sql> is formed by joining positional tokens; quote it in the shell to preserve SQL syntax.
  • --json selects DuckDB JSON output and emits an explicit [] when a successful statement has no result rows.
  • DuckDB CLI is a required optional dependency for this command.

Output and state effect#

Loads the selected data root and embedded canonical views, then gives the SQL to DuckDB and adopts its exit status. Ordinary SELECT use is read-only, but the SQL is arbitrary operator input, so any side effect requested by that SQL is owned by the operator.

Loading events and labels creates no scratch file. If either store has no partitions, its view keeps the documented column types and returns zero rows. Reading an absent data root does not create a Lake. For example, SELECT (SELECT count(*) FROM events) AS events, (SELECT count(*) FROM labels) AS labels returns both counts as zero for an empty Lake.

JSON output is streamed rather than accumulated as another in-memory result set. A successful empty or whitespace-only native result is published as [], so a caller can distinguish no matching rows from missing or malformed transport. A failed query, signal, broken output pipe or failed process wait does not manufacture an empty success; the actual status and concrete cause are retained. SQL containing several result-producing statements keeps DuckDB's result stream rather than merging distinct results into a fabricated table.

Every statement runs under the memory this machine has available when it starts, never DuckDB's own default of 80% of physical memory: on macOS the free, inactive, speculative and purgeable pages host_statistics64 reports, on Linux MemAvailable from /proc/meminfo. It runs with four DuckDB workers instead of one per core, without insertion order, and spills what does not fit to LAKE_DATA/duckdb-spill. Standard error names the limit and how it was measured: duckdb memory limit: <bytes> bytes, the memory available now (<measurement>); 4 workers; spill directory <path>. A statement that needs more than that limit even with spilling ends in DuckDB's Out of Memory Error naming the limit, instead of taking memory other processes hold until the machine stops answering.

One statement at a time runs DuckDB on a Lake root. Each statement takes the whole available memory as its limit, so statements started together would each take all of it; a statement therefore holds LAKE_DATA/duckdb-statement.lock from before it measures memory until DuckDB ends, and the file names its holder (pid <pid> (<command>) since <time>). A statement that finds the lock held waits for it, then measures the memory the first one left. Standard error says so at both ends: czekam: the DuckDB statement of pid <pid> (<command>) since <time>, so this one runs within the memory it leaves; gdzie: <lock path>; rodzaj: blokada; … and koniec czekania: …; trwalo: <seconds>s. The kernel releases the lock when its holder ends, a killed one included, so a stale file never holds a later statement. Statements on two Lake roots do not wait for each other.

Only the views the statement references are created, with the views those are written over: DuckDB binds a view when it creates it, and binding events lists every event part file, so SELECT 1 binds no view and SELECT count(*) FROM sessions binds events once, then sessions. The references are read from DuckDB's own parser (json_serialize_sql). A statement that parser does not serialize binds every view and says so on standard error: transcript-lake: DuckDB's parser does not read this statement's references (<reason>); every view is bound. The sections of views.sql, including an override in TRANSCRIPT_LAKE_SQL, each open with -- view: <name> [after <view> ...]; a section line without a view, with a word other than after, or written over a view no section creates is refused naming the line.

Exact refusals#

  • Missing or blank SQL is refused as usage: transcript-lake query [--json] "<sql>".
  • An unrecognized --wat is refused as unknown query flag: --wat.
  • Repeating --json is refused as query received duplicate --json.
  • A machine that reports no available memory is refused, retryable once other processes release memory: this machine reports no memory available for a DuckDB statement (<measurement>); the statement runs once other processes release memory.
  • A machine whose available memory cannot be read is refused naming the call that failed: cannot measure the memory available for a DuckDB statement: host_statistics64 answered kern_return <code> on macOS, cannot measure the memory available for a DuckDB statement: /proc/meminfo cannot be read: <cause> on Linux.
  • A Lake root that cannot be created, or a statement lock that cannot be opened, taken or written, is refused naming the path and the system's error: the Lake root <path> cannot be created for its statement lock: <cause>, the DuckDB statement lock <path> cannot be opened: <cause>, the DuckDB statement lock <path> cannot be taken: <cause> (a filesystem without flock, for one), the DuckDB statement lock <path> cannot name its holder: <cause>.

All long flags are exact and single-use. A value flag never consumes another --flag. Global --data-dir may appear anywhere in the invocation, must appear once, and selects an absolute root.
